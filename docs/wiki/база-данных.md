# База данных

## Что это

Игровые данные и сохранения — SQLite. База загружается в `main()`:
`Database.Load("databases/default/database.sqlite")` (`src/main.cpp:291`); без файла игра падает с
`Log(e_FatalError, ... "Could not open database")`. Путь относителен CWD — запуск из каталога сборки
с копией `data/` (см. `AGENTS.md`).

## Как устроено сейчас

`Database` — тонкая обёртка над sqlite3 (`src/utils/database.hpp`): `Load`, `Query`.
Результат — `DatabaseResult` (header + массив строк). Схемы таблиц описаны прямо в коде
(`src/league/leaguecode.cpp`) и в самих `.sqlite`-файлах; типовые таблицы:

| Таблица | Назначение |
|---|---|
| `regions`, `countries` | география (страны по регионам); `countries.tm_id` — TM-id страны (NULL у синтетической «International») |
| `leagues` | соревнования, `logo_url` (файл `images_competitions/<TM-id>.png`), `tier` (важность лиги в стране: 1 — высший дивизион, резервные/молодёжные — 90/100); `leagues.tm_id` — TM-id лиги (NULL у «National Teams») |
| `teams` | клубы и сборные: имя, лого, комплект `kit_url`, формации/тактика XML, цвета; `teams.tm_id` — TM-id клуба/сборной |
| `players` | игроки: роли, возраст, `base_stat`, `profile_xml`, внешность; `players.tm_id` — TM-id игрока |
| `tournaments`, `tournamentdata` | турниры и их данные по годам |

Колонки `tm_id` — **внешние стабильные ключи** (схема БД v2, 2026-09-09): метаданные для
матчинга в конвейере и будущих внешних ссылок (сеть/карьера/апдейты данных). Игра читает БД по
внутренним rowid (`id`) и на `tm_id` не опирается; лишние колонки ей не мешают (SELECT'ы перечисляют
нужные поля явно). NULL `tm_id` — только у синтетических строк: страна «International» и лига
«National Teams».

**Индексы** `idx_players_team` / `idx_players_national` на `players(team_id)` /
`players(nationalteam_id)` — обязательны: экран выбора команд считает на каждую команду
коррелированный `count(*)` по игрокам (`teamselect.cpp:83`), без индексов это полный скан таблицы
и ~1.5–2.5 с на лигу. Импорт создаёт их сам (`tm-gf-import/schema.py`); при ручном редактировании
БД не удалять.

Лига дополнительно создаёт в сохранении таблицы `settings`, `calendar` и колонку `stats_temporal`
(`src/league/leaguecode.cpp:104`). Сезонная статистика хранится как XML в BLOB-колонках.

## Моддинг данных игроков

Из `data/databases/modding.txt` (важно для правок):

- `profile_xml` — **распределение** навыков относительно друг друга; среднее ~0.5. Менять его —
  менять *тип* игрока, не силу.
- `base_stat` — общий уровень, пик развития ~27 лет. Сила игрока меняется через `base_stat`/`age`,
  а не через `profile_xml`.

## Сохранения лиги

Сохранения — это копии БД в каталоге `saves/` (относительно CWD):

- `CreateNewLeagueSave` копирует `databases/<srcDbName>/database.sqlite` в `saves/<name>/`,
  дополнительно создаёт `autosave.sqlite` и копирует графику команд/турниров.
- Автосейв: `SaveDatabaseToAutosave` / `SaveAutosaveToDatabase` меняют местами
  `database.sqlite` и `autosave.sqlite` (`src/league/leaguecode.cpp:157`).

## Чем ограничено

- Хранилище без миграций: изменение схемы в коде не подтянет старые сохранения.
- `Query` возвращает всё строкой — числовые поля парсятся в коде; формат и значения — в [[константы]].
- Один `Database *db` (глобальный `GetDB()`), путь к нему один — нельзя держать две базы одновременно.
