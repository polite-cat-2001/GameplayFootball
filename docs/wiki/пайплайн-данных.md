# Пайплайн данных

## Что это

Сводный **договор конвейера** Transfermarkt → GameplayFootball: из каких звеньев-репозиториев он
состоит, кто что производит, какими форматами звенья стыкуются, в каком порядке запускается полный
прогон, и как версионируются данные. Это **единственный дом**, описывающий картину целиком: агент,
которому надо понять «откуда берутся данные», начинает здесь; предметные детали конкретного формата
и маппинга — на связанных страницах и в документации самих звеньев (команды инструментов здесь **не
дублируются**, чтобы не расходиться — за ними идут в README/AGENTS конкретного репозитория).

Связанные страницы: [[данные-из-transfermarkt]] (канон, маппинг в GF SQLite, киты, калибровка),
[[база-данных]] (схема БД и её потребление игрой), [[смежные-проекты]] (экосистема), [[релиз]]
(упаковка), [[открытые-вопросы]] (статус и программа data v2).

## Лента конвейера

```
transfermarkt.com
   ▼  (HTML + внутренние JSON-API, живые запросы, кэша в API нет)
transfermarkt-api            форк FastAPI-обёртки; ни файлов не пишет, кормит скрейпер
   ▼  HTTP + CDN-картинки
transfermarkt_scrapper       краул → resume-кэш → срезы
   ▼  data/full/*.json + data/images/*
ratings-generator ─┐         (параллельны и независимы друг от друга)
kit-generator     ─┼──►  спеки + PNG/фото
tm-gf-face-generator ┘
   ▼
tm-gf-import                конвертер «канон → игровой каталог данных»
   ▼
GameplayFootball/data/databases/default   ← потребляет игра
```

### Границы контракта

Контракт между звеньями — **файлы, которые производитель пишет, а потребитель читает**. Менять
формат выхода может только владелец звена, и только синхронно с миграцией всех потребителей.
Схема выходных JSON звеньев описана в их доке; именование картинок — в коде `tm-gf-import/builders/files.py`
(источник истины — код, не проза). Три ключевых инварианта на всех границах:

1. Ключ всех сущностей — **TM-id** (см. [[глоссарий]]). БД игры хранит его в колонках
   `tm_id` (players/teams/leagues/countries) — см. «Идентичность» ниже.
2. Игра потребляет **SQLite-схему** (`[[база-данных]]`) + медиакаталог; схема создаётся в коде
   `src/menu/mainmenu.cpp` (CREATE TABLE) и `src/league/leaguecode.cpp`, отдельных `.sql` нет.
3. Файлы в git не хранятся (см. «Версионирование»).

## Полный прогон (порядок)

1. Поднять `transfermarkt-api` локально.
2. `transfermarkt_scrapper`: разведка/разметка лиг → краул профилей и составов → сборка
   `data/full/*.json` → докачка изображений. Результат — канон-срез v1 (вложенный).
3. Генераторы (`ratings`/`kit`/`faces`) — **параллельно**: каждый читает `data/full/*` и картинки.
4. `tm-gf-import` — последний: собирает БД + раскладывает файлы в целевой каталог данных игры.
5. Флаги стран (`images_countries/`, 512×512) кладутся **не** скрейпером (TM-флаги 12×7 не годятся),
   а `tools/fetch_flags.py` из репозитория игры.
6. Проверка: запуск игры против **staging-каталога** данных, затем подмена `databases/default`.

Полные команды каждого шага — в доке соответствующего репозитория.

## Идентичность

- **TM-id** — единственный стабильный внешний ключ на всех границах конвейера (имя файла фото,
  ключ JSON, id лиги в имени `images_competitions/<league_tm_id>.png`).
- Схема БД v2 (с 2026-09-09) хранит **`tm_id`** в players/teams/leagues/countries (NULL только у
  синтетических строк: страна «International», лига «National Teams»). Внутренние rowid БД игры
  (`teams.id`, `players.id` …) — **не контракт**: автоинкремент, меняются при каждой пересборке.
  Игра читает только rowid; `tm_id` — метаданные для внешнего матчинга (сеть, сохранения, апдейты
  данных). Правило: **матчинг сущностей в конвейере — только по TM-id в данной категории; имя —
  для отображения и логов** (фантом «Roberto Owono», спеллинг «Soulisack/Soulisak» — эталоны
  того, почему имя ненадёжно).
- Требование стабильности продиктовано будущим: LAN-матчи (хост шлёт клиентам снимок команд с
  хоста) и карьера (составы меняются во время игры). Стабильный ключ игрока — предпосылка формата
  «снимка команды» для провода.

## Версионирование данных

Git сгенерированные данные **не хранит** (и не должен — сотни МБ). В git живут код, вики и
**реестр** версий; сами данные — версионированные релиз-бандлы. Два уровня версий:

| Уровень | Где | Когда меняется |
|---|---|---|
| `schema_version` | `PRAGMA user_version` в БД | меняется схема/смысл колонок → нужна совместимая версия игры |
| `data_version` + `snapshot_id` | `manifest.json` рядом с БД | каждый новый срез составов/форм |

`manifest.json` пишет `tm-gf-import`: `schema_version`, `data_version`, `snapshot_id`
(дата среза TM + git-хаши инструментов), coverage-счётчики, sha256 БД. Распространение —
`GameplayFootball-data-<ver>.zip` через релизы (см. [[релиз]]). Игра логирует версию данных на
старте; при несовместимой схеме — понятная ошибка, а не молчаливая поломка.

Реестр версий (кто когда что выпустил, checksum, совместимая версия игры) — маленький
`data-versions.json` в репозитории игры (появится в data v2).

## Текущее состояние и программа data v2

- **Прод-формат канона — «v1»**: вложенный `data/full/*.json` (квирки: camelCase у клубов /
  snake_case у сборных, дубли игроков в двух клубах и в клубе+сборной — потребители дедуплицируют
  по-своему).
- В `transfermarkt_scrapper` есть готовая реализация плоского канона на TM-id
  (`data/canon/`, `build_canon.py` + `canon_schema.json`, один рекорд на игрока со связями
  `club_id`+`national_team_id`), но в проде **не используется** и имеет пробелы (цвета сборных,
  logo/flag urls).
- **Решение (2026-09-08): до первого публичного релиза делаем data v2** — «лучшую версию»:
  (1) плоский canon становится единым контрактом (доделать пробелы, prod-генерация, перевести
  четыре генератора и импорт на него); (2) схема БД v2 — **сделано (2026-09-09)**: колонки
  `tm_id` в players/teams/leagues/countries + весь матчинг данных на TM-id; осталось
  `PRAGMA user_version` + `manifest.json`; (3) сборка в staging, игра проверяется против него и
  только потом подменяется `databases/default` — **игра остаётся рабочей весь период**
  (так и прошла замена 2026-09-09). Детали и статус — [[открытые-вопросы]].

## Правила поддержки этой страницы

- Новое звено конвейера или новый формат на границе → обновить таблицу и связанную страницу
  звена тем же изменением.
- Смена потребителя формата → синхронная миграция звеньев, фиксируется здесь и в [[открытые-вопросы]].
- Запрещено: складывать сгенерированные данные в git, дублировать команды звеньев в прозе, называть
  конвертер `build_gf_database.py`.
