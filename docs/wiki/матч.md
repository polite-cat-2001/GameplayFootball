# Матч

## Что это

Симуляция футбольного матча: `Match`, `Team`, `Player`, `Ball`, судьи (`Referee`, лайнсмены) и
AI. Вся игровая логика живёт в `src/onthepitch`. Класс `Match` работает в фазах Get/Process/Put
и буферизует состояние, чтобы рендер в другом потоке читал согласованный снимок.

## Как устроено сейчас

`Match` создаётся из `MatchData` (см. [[база-данных]]) сообщением
`e_GameTaskMessage_StartMatch` в `GameTask::Action` (`src/gametask.cpp:50`).

Жизненный цикл тика (`src/onthepitch/match.cpp`):

1. **Get** — `match->Get()`: читает ввод контроллеров, накапливает команды игроков.
2. **Process** — `match->Process()`: полная симуляция — движение, мяч, касания, фолы, судьи, AI.
   Время симуляции = `EnvironmentManager::GetTime_ms() - gameSequenceInfo.startTime_ms` (тик 10 мс).
   После Process вызывается `match->PreparePutBuffers()` под `matchPutBufferMutex`.
3. **Put** — `match->FetchPutBuffers()` затем `match->Put()`: обновляет 3D-объекты, камеру, HUD.
   Дальше игроки, которым нужен апдейт модели, уходят в `UpdateFullbodyModel`/`UploadFullbodyModel`
   воркер-потоки `TaskManager` (`src/gametask.cpp:146`).

Мяч: физика без ODE — мяч двигается аналитически/с касаниями; истории мяча заданы в
[[константы]] (`ballPredictionSize_ms`, `ballHistorySize_ms`).

## Детерминизм и сериализация

`Match::Process` не зависит от реальных часов — время продвигается фиксированным шагом 10 мс
за вызов (`actualTime_ms += 10`), `BumpActualTime_ms` доступен для внешнего управления.
Это позволяет headless-прогонам быть детерминированными при фиксированном сиде.

`Match::ProcessState(EnvState*)` сериализует ядро состояния матча: игроков обеих команд
(`Player::ProcessState` / `PlayerBase::ProcessStateBase` — без внутренностей AI/humanoid),
мяч (`Ball::ProcessState`), поля матча (счёт, тайм, фазы, владение; указатели на игроков —
как ID). Используется раннером `tools/determinism` для регрессионного эталона
(см. [[архитектура]]).

Состояние стандарта хранится как `Match::setPieceType` (`e_SetPiece`), а не как отдельный
`bool`: `IsInSetPiece()` выводится из `setPieceType != e_SetPiece_None`. Тонкому клиенту
идентичность стандарта (тип + тэйкер team+slot) приезжает в снапшоте (v15, см. [[сеть]]).

## Выбор игрока и designated на стандарте

Кто считается «главным игроком у мяча» (`designatedPossessionPlayer` у `Match`,
`designatedTeamPossessionPlayer` у `Team`) определяет подсветку, HUD и камеру. На стандарте
действует особое правило: **designated отыгрывающей команды = фактический бьющий**
(`RefereeBuffer.taker`, разрешённый `TeamAIController::PrepareSetPiece`).

- Тэйкера управляемым ставит **автопереключение**, не презентация: `Team::UpdateSwitch` снимает
  свой гейт `IsInPlay()` на стандарте и выбирает `designatedTeamPossessionPlayer`, а тот равен
  бьющему. Отдельной сущности «тэйкер стандарта» нет — все потребители (`HumanController`,
  камера) читают `designatedPossessionPlayer`.
- Блок `Match::Process` (`match.cpp:1272-1288`), который считает designated по времени до мяча,
  **пропускается при `IsInSetPiece()`** — иначе его `timeRating < 0.85` затирает выбор
  автопереключения. Порядок `UpdateSwitch` → `Process` → `UpdatePossessionStats` не менялся
  (на позиции `UpdateSwitch` держится очередь `switchPriority`).
- **Вратаря можно выбирать только на стандарте** (когда он designated/бьющий): снят запрет
  `designatedTeamPossessionPlayer != GetGoalie()` и гейт ручного переключения. В открытой игре
  вратарь по-прежнему под ИИ (кроме фичи «игра за вратаря»).
- **Кнопка `Switch` на стандарте подавлена** — она занята chip-комбо. Место зарезервировано под
  меню смены бьющего (см. ниже).
- При двух локальных игроках бьющий достаётся **первому в очереди `switchPriority`**
  (round-robin `SelectPlayer`) — та же логика, что для вратаря.
- **Смена бьющего через меню** (кнопка Share / `Tab`, существующая `e_ButtonFunction_Select`):
  пока идёт стандарт, открывший меню бьющий-человек выбирает из списка активных игроков команды
  (включая вратаря) нового исполнителя. Меняется **фактический бьющий**: новый встаёт за мяч,
  старый уходит в строй; управление остаётся за открывшим меню. Навигация — стрелки/WASD,
  Enter — применить, Escape — закрыть; вне стандарта и во время заряда/полёта меню не открывается.
  Локально у каждого пира, намерение уходит на хост по существующему input-каналу.
- **Тонкий клиент**: `designatedPossessionPlayer` берётся из снапшотного тэйкера (team+slot),
  а не из подсчёта по близости (`Match::ApplyRemoteSnapshot`) — иначе камера и HUD показывали бы
  не того игрока.

## Презентация стандартов

Спека: `docs/specs/2026-09-29-setpiece-handoff.md` §2 (тикет #26). Единый объект презентации —
`SetPiecePresentation` (`src/onthepitch/setpiece/setpiecepresentation.{hpp,cpp}`), владеется
`Match` (`Match::GetSetPiecePresentation()`). Своего автомата и жизненного цикла у него нет:
фаза выводится из `RefereeBuffer.active` + `Match::IsInSetPiece()` + таймеров
(`stopTime`/`prepareTime`/`startTime`), а конец стандарта по-прежнему ставит `Referee` по
`buffer.taker->TouchAnim()`.

- **Идентичность.** На хосте `SetPiecePresentation::Process()` (зовётся из `Match::Process`
  сразу после `referee->Process()`) берёт тип из `Match::GetSetPieceType()`, тэйкера — из
  `RefereeBuffer.taker`. На тонком клиенте (`Match::Process` early-return) `SetRemoteIdentity()`
  зовётся из `ApplyRemoteSnapshot` и разрешает тэйкера из снапшота v15 (team + slot). Внутри —
  `switch (e_SetPiece)` только для расхождения по типам (какие роли доступны), класса-на-стандарт
  нет.
- **Фаза.** `GetPhase()` (`e_SetPiecePhase`): `Waiting` (buffer активен, до `prepareTime` — окно
  film-referee/карточек), `Preparing` (`prepareTime`…`startTime`, расстановка игроков — тут
  активируется камера стандарта, #27), `Active` (`startTime` прошёл, мяч живой). Фаза считается на
  лету из `buffer.active` + `IsInSetPiece()` + таймеров; на клиенте синхронизирован только тип,
  поэтому ненулевая фаза там всегда `Active`.
- **Роли** (`enum e_SetPieceRole { None, Kicker, Keeper }`): `Kicker` — если локально управляемый
  игрок == тэйкер; `Keeper` — только на пенальти, если человек управляет вратарём защищающейся
  команды. У всех прочих типов набор `{None, Kicker}`. Роль считается на каждого локального
  игрока (`GetRole(Player*)`); локальность — как в именах над игроками (`GetControllingPeerId`
  на хосте, `GetRemoteOwnerId` на клиенте). Роли `Wall` нет — стенка это ИИ-защитники.
- **HUD.** `GetHudState(Player*)` отдаёт `{ role, type, aimPoint, chargeRatio }`; отрисовка
  отдельная и идёт только при `role != None`. Сейчас это жёлтый дебаг-маркер ретикла пенальти
  (см. «Прицел пенальти» ниже): презентация хранит его состояние и рисует, локальный бьющий в
  `HumanController::Process()` скармливает сырой стик.
- **Камеры.** Пока локальный человек играет за **бьющую сторону**, или (на пенальти) за
  защищающуюся, камера стандарта стоит за мячом вместо авто-камеры (спек §4, тикет #27). Владение
  считается **по команде** бьющего (любой локальный человек на ней), а не по конкретному игроку:
  на тонком клиенте только выбранный игрок несёт remote owner id, поэтому бьющий до
  автопереключения (#29) мог бы выглядеть как ИИ, и клиент не строил бы камеру. На пенальти
  защищающемуся камера встаёт **автоматически за бьющим**, выбирать вратаря вручную не нужно:
  вратарское управление на пенальти — отдельная задача, камеру оно не гейтит. Аппликатор
  `Match::SetSetPieceCamera(eye, lookAt, fov, nearCap, farCap)` **не выключает авто-камеру**:
  складывает позу в отдельные display-поля (`Match::setPieceCamera*`) и ставит флаг
  `setPieceCameraActive`, а `PreparePutBuffers` подставляет их в буферы отображения. Живая камера
  при этом продолжает считаться (`UpdateIngameCamera` каждые 10 мс) и именно она уезжает в снапшот,
  поэтому не-владелец всегда получает **обычную** хост-камеру — и во время стандарта, и в
  удержании после удара, без «скачка» на релизе (раньше set-piece-камера подменяла живую и
  уезжала в снапшот). Раскладка look-at та же, что у `FollowCamera` (yaw →
  `setPieceCameraNodeOrientation`, pitch → `setPieceCameraOrientation`, позиция → `setPieceCameraNodePosition`);
  `FollowCamera` не трогается. Поза `eye = spot − heading*BACK + (0,0,HEIGHT)`,
  `look = spot + heading*AHEAD + (0,0,LOOK_Y)`, где `spot` — `buffer.restartPos` (z = 0) на хосте
  и позиция мяча из снапшота на клиенте (там `restartPos` на провод не идёт). Спот
  перечитывается каждый тик, пока удар не закоммичен, и замораживается на коммите: у клиента
  позиция мяча интерполирована, и в тик активации мяч может ещё лететь к точке стандарта (после
  дебаг-форса мяч телепортируется) — иначе камера замерла бы у старого мяча. `heading` — от спота
  в центр атакуемых ворот. Камеру получают только
  **пенальти, штрафной, угловой и от ворот**; аут и кикофф оставляют обычную камеру. Камера
  включается в `prepareTime` (`SetPiecePresentation::UpdateCamera`, зовётся из `Match::Process`
  после фол-камеры, поэтому film-referee отдаёт управление в этой точке), а scorer-cam сохраняет
  приоритет (`IsGoalScored()` снимает камеру). Позы и клипы — [[константы]]. Релиз:
  `HumanController` уведомляет носителя в момент коммита действия (`NotifyKickerCommitted`) —
  пенальти держит `_default_SetPiece_CamHold_ms` (1.5 с) после отпускания, штрафной-удар — 1.5 с,
  штрафной-пас/навес, угловой и от ворот уходят в момент отпускания; при просмотре поза заморожена.
  Уже отпущенная камера не включается заново до конца этого стандарта (защёлка `camSuppressed`),
  иначе релиз и ещё живой стандарт (мяч не коснулись) мигали бы камерой каждый тик.
  На тонком клиенте камера строится локально в `ApplyRemoteSnapshot` (спот — из позы мяча), но
  включается, только когда тип доедет снапшотом (снапшот везёт тип с `startTime`, не с
  `prepareTime`), т.е. позже, чем на хосте. Не-владелец set-piece-камеру не получает вообще: клиент
  копирует обычную хост-камеру, а локальный display-override включается только у владельца. Прицел
  подач, вращающий `heading`, — тикет #28.

## Варианты удара (curl/chip)

Тип удара фиксируется в момент **нажатия** `Shot` и несётся в ударную команду полем
`TouchInfo::shotType` (`enum e_ShotType { e_ShotType_Normal, e_ShotType_Curl, e_ShotType_Chip }`
в `src/gamedefines.hpp`). Действует и для обычного, и для одно-касания/queued удара.

- curl = `R2` (Dribble) + Shot / `C` + `D`; chip = `L1` (Switch) + Shot / `Q` + `D`.
- Оба модификатора зажаты одновременно (или ни одного) → `e_ShotType_Normal`.
- Новых `e_ButtonFunction` не заводится: переиспользуются `Dribble`/`Switch`/`Shot`,
  `defaultKeyIDs` не меняется.
- Пока идёт заряд варианта, подавлены knock-on и super-cancel
  (`HumanController::IsChargingShotVariant`); пока идёт заряд chip, `Switch` не переключает
  игрока (`HumanController::IsChargingChip` в гейте `Team::Process`).

### Расчёт траектории

Общий расчёт удара вынесен в чистый модуль `src/onthepitch/setpiece/setpiecelogic.{hpp,cpp}`
(без `Match`/`Player`, пригоден к headless-прогону). Удар запускается **баллистически** в точку
на линии атакующих ворот (`x = side · -pitchHalfW`, латераль клампится у створа): высота прицела
растёт с зарядом (`_default_Shot_AimYMin` 0.8 → `goalHeight + _default_Shot_OverLift` 3.5 м),
вертикальная скорость — из `vz = Δz/t + ½g·t` с потолком `_default_Shot_MaxLift` 12. Поэтому
заряд управляет высотой: слабый/средний заряд ложится в створ, сильный задирает в верхний угол и
**может перебить выше ворот** (паритет FIFA/PES: «не заливай шкалу — перебьёшь»). Короткий тап
(заряд < `_default_Shot_GroundChargeMax`) — настильный удар низом со скоростью не ниже
`_default_Shot_GroundPower`.

- **Curl**: доворот прицела наружу `_default_Shot_Curl_AimOut` + боковое вращение
  `_default_Shot_Curl_ZRot` через `Ball::SetRotation` (Магнус в мяче уже включён); низом
  обнуляется только вертикаль, вращение остаётся. Направление закрутки — **вход из `TouchInfo`**
  (поле `curl`, знак выводится из прицела в `PlanShot`, а не из случайного корпусного
  `bodyTouchAngle`). Как finesse в FIFA/PES, curl **отдаёт часть силы** за точность:
  горизонтальная скорость × `_default_Shot_Curl_SpeedFactor`. Спин и доворот настраиваются
  ползунками настроек геймплея (`gameplay_shot_curlspin` / `gameplay_shot_curlaimout`, с показом
  числа).
- **Chip**: фиксированный крутой угол вылета `_default_Shot_Chip_Angle`, а **заряд задаёт
  общую скорость** (доля `_default_Shot_Chip_SpeedFactor` от силы удара). Поэтому тап — короткий
  подброс через выбежавшего вратаря, сильнее — дальше и выше, полный заряд перелетает
  (паритет FIFA/PES: «power is everything»); низом chip не режется.
- Удар заряжается `KICK_CHARGE_MAX_TIME` (0.5 с), пасы — 1 с; на полном заряде автовыстрел.
- Планировщик `setpiecelogic::PlanShot` кладёт направление/мощность/высоту (`TouchInfo::aimHeight`)
  и тип (curl-план) в `TouchInfo`; один путь для `HumanController` и `ElizaController`
  (ИИ-исполнитель пенальти тоже зовёт планировщик). Физическую скорость и разброс по навыку
  считает `Humanoid::GetShotVector`.

### Прицел пенальти

Отдельно от прицеливания подач (§6) — 2D-ретикл на плоскости атакующих ворот (тикет #25).
Состояние ретикла (латераль/высота, фиксация) живёт в `SetPiecePresentation` (см. «Презентация
стандартов»), чистые функции — в `setpiecelogic` (`DefaultPenaltyAim`, `UpdatePenaltyAim`,
`PlanPenaltyShot`); `HumanController` только скармливает ввод и читает прицел при ударе.

- **Ретикл** (`PenaltyAim`: латераль, высота): стик двигает точку со скоростью
  `_default_Pen_ReticleSpeed`; без ввода — плавный возврат к центру
  (`_default_Pen_ReticleReturn`); кламп `±(goalHalfWidth + _default_Pen_AimOverhang)` и
  `0..(goalHeight + _default_Pen_AimOverhang)`. Горизонталь переводится в мир через сторону
  бьющего: камера пенальти смотрит из спота в атакуемые ворота (`x = -side*pitchHalfW`), поэтому
  «вправо по экрану» — это мировой `+y` при `side == 1` и `-y` при `side == -1` (после смены
  сторон во 2-м тайме знак меняется). Жёлтый дебаг-маркер ставится в точку на линии ворот
  (`SetYellowDebugPilon`).
- **Фиксация**: в момент нажатия `Shot` маркер замирает; на отпускании удар летит в точку плюс
  выборка из диска разброса (радиус `_default_Pen_SpreadMinR`→`_default_Pen_SpreadMaxR` по
  заряду), горизонтальная скорость `_default_Pen_PowerMinSpeed`→`_default_Pen_PowerMaxSpeed`.
- **Авто-аим отключён**: для пенальти `AI_GetShotDirection` не зовётся.
- **`GetShotVector`**: ветка `TouchInfo.useAimTarget` берёт латераль/высоту/скорость из
  `TouchInfo`, считает вертикаль баллистикой без потолка `_default_Shot_MaxLift`, пропускает
  worst-case по навыку и боковую кривую корпуса; пенальти никогда не считается низовым ударом.
- После розыгрыша стандарта маркер и ретикл сбрасываются.

Прицел — презентация, хеш `tools/determinism` не меняет; сам удар идёт обычным gameplay-путём
(`TouchInfo`). Дебаг-активация пенальти клавишей `P` — тикет #39.

## Ручной режим и бинды в открытой игре

Кнопка `Special` (`L2` / клавиатура `Z`) — «ручной режим» (`HumanController`):

- **с мячом** (`hasPossession`) — рывок партнёра (`TeamAIController::ApplyAttackingRun`) в
  `Process()`; плюс стоп-на-месте в `_GetHidInput()`, когда designated possession = управляемый
  (сырая скорость = `idleVelocity`).
- **без мяча** (`!hasBestPossession`) — super-cancel: движение идёт строго по стику, без
  автоподсказки (`command.desiredDirection`/`desiredVelocityFloat` = сырой ввод).

**Knock-on** — двойной тап `Sprint` (`R1` / `E`): две пресс-эджи в окне
`sprintDoubleTapWindow_ms` вооружают `e_PlayerCommandModifier_KnockOn`; одиночный тап —
обычный спринт. Заряд живёт ограниченное время `sprintKnockOnWindow_ms`: пока он активен,
модификатор кладётся в touch-командования (`_BallControlCommand`/`_TrapCommand`) и срабатывает
на кадре касания мяча; удержание кнопки заряд не продлевает. Поэтому после проброса удержанный
`Sprint` снова даёт обычный спринт, а не повторные пробросы. Окно намеренно длиннее одной
ballcontrol-анимации, чтобы модификатор доживал до её touch-кадра.

Комбо `Dribble`+`Sprint` удалено. `Dribble` (`R2` / `C`) остаётся ведением и модификатором
curl; `Switch` (`L1` / `Q`) — переключение игрока и модификатор chip. `IsChargingShotVariant`
по-прежнему подавляет knock-on и super-cancel во время заряда варианта удара.

## AI игроков

Каждым игроком управляет контроллер (`IController`). Боты — `ElizaController`
(`src/onthepitch/player/controller/elizacontroller.hpp`):

- стратегии вне мяча — `Strategy` и наследники в `strategies/offtheball/` (offense, defense, midfield, goalie);
- `MentalImage` — «ментальный образ» последних ~секунд матча, из которого стратегии принимают решения;
- пас ищется перебором кандидатов с рейтингом `PassRating` (шанс на успех, позиция, ситуация);
- празднования — `strategies/special/celebration.hpp`.

Владение человеком — `HumanController`/`HumanGamer`; судьи — `RefereeController` и `Playerofficial`.
Команды игроков — `PlayerCommand`/`PlayerCommandQueue` (`src/gamedefines.hpp:254`).

### Имена над игроками

Подпись (имя) рисуется над игроком в `Player::Put2D` по буферу
`fetchedbuf_nameCaptionShowCondition` (`src/onthepitch/player/player.cpp:353`). В обычном
режиме (`GetDebugMode() == Off`):

- команда с человеком — подпись над **выбранным** (управляемым) игроком (`IsHumanControlled`);
- команда полностью под ИИ — подпись над **владеющим** игроком
  (`GetDesignatedTeamPossessionPlayer`).

Текст — `PlayerData::GetLastName()`; для игроков без фамилии (Transfermarkt хранит их под одним
именем) возвращается имя (`src/data/playerdata.hpp:23`), иначе подпись была бы пустой.

**Ловушка**: `Gui2Caption::SetCaption` (`src/utils/gui2/widgets/caption.cpp:119`) переводит текст
в верхний регистр. Побайтовый `::toupper` ломал UTF-8-фамилии с акцентами (í, á, é) — подпись
над таким игроком не отрисовывалась вовсе. Сейчас верхний регистр применяется только к ASCII,
байты UTF-8 не трогаются.

**Ловушка (асинхронные текстуры)**: 2D-текстуры создаются асинхронно (`Texture::CreateTextureAsync`,
без `Wait()` — ради скорости загрузки меню). Подпись в конструкторе сразу ресайзится (текст шире
исходной картинки), и `Texture::ResizeTexture` использовал `textureID` напрямую с
`assert(textureID != -1)`: если асинхронное создание ещё не успело (ID = -1), ресайз молча
проваливался, текстура оставалась крошечной/пустой, а `UpdateTexture` (`glTexSubImage2D`) размер
не меняет → подпись не видна. Зависело от тайминга рендер-потока — отсюда нестабильность
(то есть, то нет, у разных игроков/запусков). Фикс: `ResizeTexture` тоже резолвит ID на
рендер-потоке в момент выполнения (`Renderer3DMessage_ResizeTexture` теперь принимает
`Resource<Texture>`, как `UpdateTexture`), FIFO-очередь гарантирует, что create отработал раньше.

## Замены и роли

Замены доступны **во время матча** из экрана плана (`GamePlanPage`, открывается из
пауза-меню и из [[сеть|сетевого]] оверлея). Модель:

- Лимит `maxSubstitutions` (5) на команду; действующие — `Team::CanSubstitute()`.
- План строится по **активным** игрокам (`Team::GetActivePlayers`) и их ролям из
  `runtimeFormation`; лавка — по неактивным. Обмен «полевой ↔ запасной» ставит замену,
  повторный выбор той же пары — отменяет (`Match::CancelSubstitution`).
- **Очередь нормализуется** (`Match::NormalizePendingSubstitutions` и та же логика в
  `GamePlanPage`): цепочка `X→Z`, `Z→W` схлопывается в `X→W`, а `X→Z`, `Z→X` — в ноль;
  поэтому «циклические» замены дают правильный нетто-результат.
- **Вернуться на поле нельзя.** Ушедший игрок (заменённый или удалённый) попадает в
  `Team::leftPitch` (`HasLeftPitch`/`MarkPlayerLeftPitch`); `Team::Substitute` и
  `Match::QueueSubstitution` его не пускают обратно, а экран плана показывает его на
  лавке серым с пометкой `(out)` и не даёт выбрать (`GamePlanPage`). В `Player::SendOff`
  (красная карточка) игрок тоже помечается ушедшим.
- **Схема обновляется сразу**: как только замена поставлена в очередь, карточка
  уходящего уезжает на лавку, а приходящего встаёт на его позицию/роль (метки `-`/`+`);
  фактические замены по-прежнему применяются на рестарте. Пересборка экрана отложена в
  `GamePlanPage::Process`, чтобы не удалять кнопку внутри её же обработчика клика.
  **Портрет следует за игроком слота**: в матче карточки пересобираются, а в пре-матче
  обмен (`PerformAction` → `TeamData::SwitchPlayers`) обновляется на месте через
  `RefreshPanel`, который догружает фото по `tm_id` (`Gui2Image::LoadImage` — no-op, если
  путь тот же).
- **Read-only соперник тоже живой.** В однопанельном режиме чужая команда рисуется
  `GamePlanPage::BuildOpponent`; в матче она берётся из **живого** `Team`
  (`GetAllPlayers` + `runtimeFormation`), а не из `TeamData`, иначе после замены
   соперника на хосте (или после его же замены на клиенте) на панели оставался
   старый игрок. Без матча (пре-матч) источник по-прежнему `TeamData`.
- **Карточки поля: фото задаёт ширину, текст не выходит за плашку.** Фото — портретная вырезка игрока по
  `players.tm_id` (`databases/default/faces/<tm_id>.png`, 160×208, иначе
  `player_placeholder.png`); ширина фото задаёт ширину карточки, высота —
  `ширина × 208/160` (`photoAspect`); строка «позиция + рейтинг» и имя — плашки ровно той же ширины
  (PES-style), а снизу карточку завершает тонкая полоса усталости (`DrawFatigueBar`:
  непрозрачный трек + заливка цветом `FatigueColor` по проценту). Имя и позиция
  обрезаются по ширине плашки с точкой (`FitNameCaption`, UTF-8-безопасно); полное имя
  выбранного игрока — в нижней инфо-полосе. Имя — **обычный текст** (`Gui2Caption`), а
  не подпись кнопки: кнопка накрывает всю карточку, но в режиме «только рамка» с
  отключённой отрисовкой (`Gui2Button::SetFrameOnly` + `SetDrawFrame(false)`) не рисует
  ничего и лишь принимает клики. **Выделение (курсор/held) — белая обводка по контуру
  фото** (`Gui2Image::SetDrawOutline`, радиус 4): для карточки заранее готовится вторая
  копия фото с контуром и показывается вместо обычной; квадратной рамки больше нет.
  Карточки ставятся прямо по позициям формации/схемы (`PositionPitchCard`:
  центр фото на якоре, зажим в границы поля — как было изначально); **ни расталкивания,
  ни дополнительных отступов нет** — плашка сужена до ширины фото, поэтому соседи по
  формации и так не пересекаются, а расталкивание искажало вид схем. Якорь формации
  (`entry.pos`) не меняется, поэтому навигация курсором работает по-прежнему. Раскладка
  едина для редактируемой панели (`PreviewSchemes`) и read-only соперника
  (`BuildOpponent`; у него нет полосы усталости). Портретные фото выше прежних
  квадратных, поэтому карточки могут пересекаться; **все фото — отдельный слой поверх
  текста** (`Gui2View::SetOverlay`, z-priority +1): при наложении фото перекрывает
  имя/позицию соседа, а не наоборот. Фланговых игроков при отрисовке **поджимает внутрь
  до ±0.75 по ширине** (`CardAnchorPosition`/`pitchCardMaxSide`): сами схемы уже запекают
  этот лимит в позиции LM/RM, а формации из БД (начальная тактика) — нет, из-за чего их
  карточки упирались в край. Это только раскладка, реальная формация не меняется.
  Пороги — в [[константы]].
- **Условие игрока** выводится справа от рейтинга у каждой записи плана, включая лавку:
  `GetFatigueFactorInv()` × 100 %, цвет по шкале голубой (свежий) → зелёный → жёлтый →
  оранжевый → красный (выжат), пороги — в [[константы]]. Источник — живой `Team` панели
  (`GamePlanPage::EntryFatigue`); у запасных и в пре-матче тика нет, поэтому всегда 100 %.
  Тонкому клиенту значение приходит в снапшоте (`SnapshotPlayer::fatigue`, протокол v9,
  см. [[сеть]]), иначе он показывал бы всех свежими.
- Замена **не применяется мгновенно**: `Match::QueueSubstitution` кладёт её в очередь, а
  `Match::ApplyPendingSubstitutions` выполняет на ближайшем возобновлении игры (рестарт,
  `src/onthepitch/referee.cpp`), затем заново считает расстановку set-piece. Пришедший
  игрок наследует роль/позицию ушедшего (`Team::Substitute` → `runtimeFormation`),
  уходящий деактивируется. Форму приходящий берёт из **рантайм**-номера кита
  (`Team::kitNumber`, его меняет `SetKitNumber`), а не из очереди матча — иначе
  после смены кита по ходу матча замена выходила в старой форме.
- Применённая замена пишется в `substitutionNotices`; в верхнем углу показывается
  «X off, Y on». Пачка замен, применённых за один рестарт, выводится **списком строк
  одновременно** (`Match::ShowSubstitutionNotices`, пул подписей), а не по одной.
  Состояние транслируется в снапшот для тонких клиентов (см. [[сеть]]).
- **Гонка активации (важно).** `Player::Activate` создаёт `humanoid`/подписи и только
  **последним** ставит `isActive = true`; `Player::Deactivate` — наоборот, снимает флаг
  **первым**. Иначе воркер графики (`GameTask::PutPhase` → `Match::Put` → `Team::Put2D`)
  видит активного игрока с ещё не созданной моделью и падает по `humanoid == 0`
  (`Put2D`/`Hide2D` дополнительно защищены проверками). Структурные правки сцены
  (создание модели) идут под `getPhaseMutex`; он же взят в `GraphicsTask::ProcessPhase`.
- **Локальная игра вдвоём** (и в пре-матче, и в матче). Если две стороны под локальным
  управлением (по `MenuTask::GetControllerSetup`), экран показывает
  **обе** команды сразу: у каждой своя схема и лавка справа от неё, у каждой — свой курсор.
  Панели раскладываются слева-направо по выбранной стороне (`SideSelection::side`: −1 слева,
  +1 справа), а не по порядку устройств — клавиатура не обязательно `controllerID 0`, иначе
  команды путались местами.
  В сетевом матче сторона берётся из авторитетного лобби (`MenuTask::GetLocalNetworkTeamID`,
  `LobbyState`), а не из `ControllerSetup` (зеркальный экран сторон его не заполняет):
  редактируется только команда локального пира, соперник — read-only. Ориентация как
  в матче: своя команда слева (home) или справа (away), лавка — справа от неё,
  соперник — с противоположной стороны (для гостя раскладка зеркалится).
  В пре-матче панели правят `TeamData` из `MatchData`, в матче — живые `Team`.
  Ввод читается **напрямую с устройства** игрока (как в выборе сторон), а не через единый
  фокус GUI2; у ИИ-команды лавки и управления нет. Выход — голосованием: Back/B отмечает
  «готов», любое **новое** нажатие/наклон снимает готовность и возвращает к выбору состава
  (отпускание стика не считается), выход когда готовы все. Навигация курсора выбирает
  ближайшего игрока **вдоль** направления с ограничением бокового смещения (иначе на
  вытянутом по вертикали поле дальний, но «ровный» защитник перебивал ближнего ЦЗ).
  Управление — стик **и крестовина**: функции движения замаплены на оси, поэтому
  D-pad читается напрямую `UserEventManager::GetJoyButtonState(SDL_GAMEPAD_BUTTON_DPAD_*)`
  (как в выборе команд), иначе переключение между игроками крестовиной не работало.
  В остальных режимах (1 игрок / против ИИ / сеть) — прежний однопанельный экран.
- **Групповые решения при игре вдвоём.** Старт матча из пре-матч хаба
  (`PreMatchPage`) и снятие паузы (`IngamePage`, кнопка «Continue») требуются от
  **обеих** сторон: каждая подтверждает своей кнопкой (клавиатура — Enter, геймпад —
  A), показывается счётчик `1/2`. GUI-активация кнопки в этом режиме — заглушка
  (`GoStartMatch`/`VoteResume` ничего не делают), голоса собираются с устройств
  напрямую и адресуются по `controllerID` (`MenuTask::GetLocalSideDevices`), как в
  сетевом голосовании (`PreMatchPage::ToggleLocalStartVote`,
  `IngamePage::ToggleLocalResumeVote`). Back в хабе снимает уже поставленную
  готовность к старту и возвращает на вкладку Kick-off
  (`PreMatchPage::CancelLocalStartVote`/`FocusKickOffTab`). На общем экране подпись
  кнопки нейтральна — «Start match (N/2)», а не «Cancel start»: она не знает, какому
  игроку показана, и для ещё не голосовавшей стороны «Cancel» врал бы (нажатие
  запускает матч). Условие — `MenuTask::HasTwoLocalPlayers`
  (две разные стороны на двух разных локальных устройствах); иначе, как и раньше,
  старт/продолжение мгновенные. В паузе матча **Back (Esc/B) равнозначен Continue**:
  тот же голос, повторное нажатие снимает готовность (сетевой `VoteResume` и локальные
  сырые обработчики `ProcessKeyboardEvent`/`ProcessJoystickEvent`; windowing-Escape в
  локальном режиме глушится, чтобы не уйти `GoBack`).
- **Пре-матч хаб: капитаны и формы.** По бокам от контента хаба
  (`PreMatchPage`) рисуются две 3D-модели капитанов (по одной на команду) в
  выбранной форме и спокойной idle-позе — `PreMatchCaptainPreview`
  (`src/menu/startmatch/prematchcaptain.*`). Модель — приватная копия
  `fullbody.object` (уникальный суффикс ресурса, иначе `FetchCopy` кэширует чужой
  kit), поза — порт бейка `HumanoidBase` по кадру `movement/idle/000_idlelevel1.anim`,
  рост нормализуется. Рисует её **камера меню-сцены** (отдельный camera-view не
  заводится): модели — `ScreenAnchor` в `MenuScene`, их трансформ пересчитывается
  вместе с камерой под `getPhaseMutex`, а объекты помечены `no_cull`, чтобы
  консервативные плоскости отсечения камеры их не выкидывали. Вкладка **Kit** —
  реальный выбор комплекта: пулдауны перебирают существующие `<club>_kit_01..06.png`,
  выбор пишется в `MenuTask::SetTeamKitNum` (сток `Team::InitPlayers`) и перекрашивает
  модель. **Формы — чисто локальная настройка**: каждый пир выбирает и себе, и
  сопернику, по сети это не передаётся (см. [[сеть]]).
- **Роли** (`e_TeamRole`: капитан, пенальтист, штрафные ближний/дальний, угловые
  левый/правый). Назначенный исполнитель хранится в `MatchData` **по слоту состава**
  (`MatchData::SetRolePlayer`/`GetRolePlayer`, -1 = не задан), поэтому одно значение
  валидно и в пре-матче (`TeamData`-слот), и в матче (`Team`-слот) и не зависит от
  процесс-глобального `PlayerBase::id`. Рантайм — `Team::GetRoleSlot`: слот, если
  назначенный игрок ещё на поле, иначе **лучший подходящий активный игрок**
  (`Team::SuggestRoleSlot` + `TeamRoleSuitability`; вратарь исключён). «Лучший» —
  детерминированный бленд статов (`teamdata.cpp`), общий для ИИ и пре-матч-подсказки
  в плане игры. Если назначенный игрок покинул поле, `GetRoleSlot` снова выбирает
  лучшего; `TeamAIController::PrepareSetPiece` берёт `GetRolePlayer` для пенальти и
  угловых, а для штрафных — исключение: **на своей половине берётся ближайший**
  (это вынос), **на чужой — назначенный ближний/дальний** (ближний = в радиусе
  `freeKickNearDistance` от ворот, см. [[константы]]). Роли правит раздел **Roles**
  экрана плана (см. ниже).
- **Тактические схемы** (раздел **Tactics**). Схемы захардкожены в
  `src/menu/tacticschemes.cpp` (4-4-2, 4-3-3, 4-2-3-1, 3-5-2, 5-3-2, 4-5-1); позиция
  каждой роли адаптируется той же формулой, что и формации команд
  (`databasePosition * 0.6 + GetDefaultRolePosition(role) * 0.4`, см. [[база-данных]]).
  Центральная линия полузащиты (роли DM/CM) во всех схемах поднята на +0.15 глубины;
  крайние (LM/RM) сдвинуты внутрь до ±0.75, чтобы карточки не выходили за линию поля
  (в 4-2-3-1 это фланговые атакующие).
  Пока любой раздел открыт, **кнопки панели (Tactics / Positions / Roles) скрыты** —
  они возвращаются при выходе обратно на панель (**Back**); подпись-описание активного
  раздела остаётся. Пока раздел открыт, **колонка лавки превращается в список схем**; листание
  **предпросматривает** подсвеченную схему на поле, **Enter/A фиксирует** её,
  **Back/Esc/B** возвращает к панели и откатывает неподтверждённый предпросмотр.
  Расстановка игроков — оптимальное назначение (венгерский метод, `src/misc/hungarian.c`):
  вратарь закреплён, остальные получают позиции схемы с минимумом суммы «дистанция +
  штраф за чужую линию» (защита/полузащита/атака). В пре-матче схема пишется в
  `TeamData` (`ApplySchemeToTeamData`), в матче — в рантайм-формацию живых игроков
  (`Team::SetRuntimeFormationEntry`, `ApplySchemeToTeam`), поэтому ИИ и запасные
  подхватывают новую расстановку. В сети правка host-authoritative (см. [[сеть]]).
  Текущая схема подсвечивается в списке, если формация совпадает с одной из известных.
- **Роли** (раздел **Roles**). Пока раздел открыт, **полоса между полем и панелью
  разделов** (`GamePlanPage`, `BuildRoleList`) становится списком ролей в порядке
  «капитан, штрафной дальний, штрафной ближний, пенальтист, левый угловой, правый
  угловой» (`planRoleOrder`; имена — `GetTeamRoleName`). В строке справа — текущий
  исполнитель: назначенный слот или, если роль не задана, лучший подходящий игрок
  (тот же `TeamRoleSuitability`, что у ИИ), так что список сразу показывает
  осмысленный выбор. **Up/Down** листает, **Enter/A** открывает выбор игрока,
  **Back/Esc/B** возвращает к панели. При выборе список скрывается и в той же полосе
  показывается карточка наводимого игрока (`rolePicker*`); стрелки водят курсор
  **только по полю** (`FindNextEntry(..., onlyPitch)`), **Enter/A** фиксирует
  игрока и возвращает к списку, **Back/Esc/B** отменяет выбор и тоже возвращает к
  списку (двухуровневый Back: выбор → список → панель). В пре-матче выбор пишется в
  `MatchData`, в матче — через живой `Team` (то же `MatchData`); в сети
  host-authoritative (см. [[сеть]]).

## Отладочные хоткеи

Работают в матче, для ручного тестирования (локально, не через сеть):

- **`F1`** — перегенерировать параметры солнца (погода).
- **`F2`** — убрать/вернуть за пределы поля полевых игроков команды **без живого человека**
  (вратарь остаётся в воротах). `Match::DebugParkOpponents`; пока тумблер `debugRemoveOpponents`
  включён, позиция переставляется каждый тик, чтобы ИИ их не увёл обратно. Команда с человеком
  и вратарь не трогаются.
- **`P` / `Alt+P`** — форсировать пенальти в атакуемые / в свои ворота; **`F` / `Alt+F`** —
  штрафной; **`Y` / `Alt+Y`** — угловой. Без `Alt` стандарт отыгрывает команда **локального пира**
  (человек бьёт), с `Alt` — соперник (человек защищает: вратарь на пенальти, стенка на штрафном).
  Команда определяется по `GetControllingPeerId == GetLocalPeerId`, а не по «есть человеческий
  игрок» — иначе в сети с двумя людьми всегда выбиралась бы команда 0. Форсирование —
  `Referee::DebugForceSetPiece(e_SetPiece, teamID, restartPos)` + штатный `PrepareSetPiece`; в
  сети клавиши обрабатывает только хост (`Match::Process` на клиенте early-return). Клавиши
  работают **только из чистого игрового состояния** — не во время стандарта и не во время
  празднования гола (`IsInPlay() && !IsInSetPiece()`). Позиции: пенальти 11 м, штрафной 25 м по
  центру, угловой — флажок атакуемых ворот. Что бьющий реально остаётся под человеком — на
  `Team::UpdateSwitch`/designated (тикет #29).

## Чем ограничено

- Ввод в фазе Get, симуляция в Process, рендер-данные в Put — читать/писать состояние вне
  своего буфера нельзя без мьютекса (см. [[архитектура]]).
- `time_ms` — глобальный источник времени; `GetMatchTime_ms()` — внутриигровое время матча,
  они не равны (паузы, реплеи).
- Состав и роли можно менять в матче, но изменения живут только в рантайме (`MatchData`/
  `runtimeFormation`) и не сохраняются в БД; персистентная правка — через рестарт матча.
