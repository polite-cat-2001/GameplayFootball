Дата: 2026-09-29. Тип: spec (хендофф). Статус: решения зафиксированы картой
[Порт фич из open_football: стандарты, удары, сетка, вратарь](https://github.com/polite-cat-2001/GameplayFootball/issues/1);
по документу можно начинать кодить без дополнительных решений. Неизменяемый снимок — правки
вести в вики, а не сюда.

Референс: `open_football` @ `C:\Users\Egor\Desktop\projects\open_football`, ветка
`feat/ai_standards` (HEAD `d27fe6e`). Планка — приближение по ощущению, не точный паритет.
Все числа — только в `src/gamedefines.hpp` и в `docs/wiki/константы.md`.

## Контекст и цель

Перенос в GF четырёх связанных фич из open_football: (1) стандарты и их презентация
(камера, прицел, разбег, бьющий), (2) варианты удара curl/chip, (3) игра за вратаря и
оборона пенальти, (4) колыхание сетки. Движок GF — host-authoritative тонкий клиент:
архитектурные решения обязаны с самого начала учитывать `src/net`.

Спека нитей:

- **Общее правило**: геймплейные состояния синхронизируем, презентационные — локально.
- **Презентация vs физика**: камеры и прицел — только для человека; расчёт самого удара
  (низом / крученый / черпачок) — общий код, пригодный и для ИИ. ИИ-тайкер через
  презентацию не идёт.
- **Детерминизм**: презентация (камеры, прицел, сетка) не меняет хеш `tools/determinism`;
  gameplay-механики (curl/chip, состояние вратаря, стенка, разбег, автопереключение)
  меняют → требуют перегенерации эталонов.

## 1. Сетевая классификация состояний

Источник: [Сетевая классификация состояний новых фич](https://github.com/polite-cat-2001/GameplayFootball/issues/2).

Модель остаётся host-authoritative thin client: снапшот — поток позы рендера, а не
sim-состояние. Симуляцию целиком считает хост; клиент применяет позы (`SnapshotPlayer` из
`animApplyBuffer`) и трансформ мяча (`ballPosition`/`ballOrientation`), не вызывая
`Match::Process`. «Геймплейное» ≠ «обязано быть в снапшоте»: результат симуляции и так
доезжает позой/мячом. Классификация в три корзины:

- **A — host-симуляция**: считается на хосте, отдельно не сериализуется, результат виден
  через позу/мяч. Меняет хеш `tools/determinism`.
- **B — gameplay-состояние, нужное клиенту для локальной отрисовки**: в снапшот.
- **C — презентация**: локально у каждого пира, не сериализуется никогда.

Разбор по фичам:

| Фича | Состояние | Корзина | В снапшоте / реплее? |
|---|---|---|---|
| Тип удара (обычный / curl / chip) | `rotation_ms` + Magnus → траектория | A | Нет. Тип выводится хостом из битмаски кнопок + стика, что клиент уже шлёт в `NetInputFrame`; результат — `ballPosition`/`ballOrientation`. Спин не шлём. Меняет хеш. |
| Прицел / ретикл | направление + нажатие до удара | ввод, не B/C | Нет. Наводка — intent, едет по input-каналу (`NetInputFrame.direction`); ретикл — C. Отдельного поля не заводим. |
| Камеры стандартов | позы камеры | C (+ B) | Камера локальная у каждого пира; чтобы выбрать per-piece камеру, клиенту нужен тип стандарта и исполнитель — это корзина B. |
| Тип стандарта / исполнитель | `e_SetPiece`, taker team+slot | B | **Да — единственное расширение снапшота.** Заменяем `bool inSetPiece` на `e_SetPiece` + слот исполнителя; `inSetPiece` выводится (`type != None`). Bump протокола `v14 → v15`. |
| Состояние вратаря | `ballRetainer`, retain-анимация, HANDS/OUTFIELD/RETURNING, таймер 6 с | A | Нет. Клиент воспроизводит позой + приклеенным мячом. HUD-подсказки — из `animID`/`ownerId`. Ввод вратаря — по input-каналу. |
| Сетка | NetSim | C | Нет. Presentation-only, derived из мяча. Клиент считает NetSim локально от интерполированной позы мяча; в реплее — от записанной позы. |
| Реплей | `ReplaySpatial` (position/orientation) + мяч | — | Новых каналов нет. Позный реплей воспроизводит curl/chip, вратаря, мяч; сетка выводится из записанной позы; камера реплея — отдельная, не per-piece. |

**Итог по `matchsnapshot.cpp`**: единственное расширение — тип стандарта + фактический
тэйкер (B), больше ничего не сериализуем. `roles[2][e_TeamRole_SIZE]` (план-роли, в
протоколе с v12) остаются для редактирования роли в плане игры и тэйкера **не заменяют**
(план-слот может быть `-1` или не совпадать с фактическим; fallback `SuggestRoleSlot` /
ближайший).

## 2. Шов презентации стандартов

Источник: [Шов презентации стандартов в движке](https://github.com/polite-cat-2001/GameplayFootball/issues/3).

Шов — **лёгкий GF-native слой презентации**, не порт per-standard Node-контроллеров из
`open_football`. Судья уже владеет жизненным циклом стандарта (`RefereeBuffer`), поэтому
параллельный слой контроллеров продублировал бы его.

1. **Носитель.** Один объект презентации, владеемый `Match`, читает тип стандарта и тэйкера
   из `RefereeBuffer` (`Match::GetRefereeBuffer()`, `match.hpp:217`). Расхождения по типам —
   `switch (e_SetPiece)` внутри него, без класса-на-стандарт. Свой автомат не заводится:
   фаза выводится из `RefereeBuffer.active` + `IsInSetPiece()` + таймеров
   (`stopTime/prepareTime/startTime`). Жизненный цикл остаётся у `Referee`
   (`referee.cpp:68-267`), конец — по `buffer.taker->TouchAnim()` (`referee.cpp:239`).
2. **Роли.** `enum e_SetPieceRole { None, Kicker, Keeper }`. `Wall` не заводим — стенка это
   ИИ-защитники. Роль — на локального человека: `Kicker`, если управляемый игрок ==
   `buffer.taker`; `Keeper` только на пенальти, если человек управляет вратарём защищающейся
   команды. По типам: пенальти → `{None, Kicker, Keeper}`; все прочие (штрафной, угловой,
   аут, от ворот, кикофф) → `{None, Kicker}`. При двух локальных игроках роль считается на
   каждого.
3. **Камера.** Переиспользуется override-паттерн фол-камеры (`match.cpp:1394-1408`):
   презентация отдаёт цель+зум, `Match` применяет через `SetAutoUpdateIngameCamera(false)` +
   `FollowCamera`. Камера ведётся только когда роль владеет камерой.
4. **Общий расчёт удара.** Новый чистый модуль `src/onthepitch/setpiece/`
   (`setpiecelogic.{hpp,cpp}`): планировщик возвращает `(desiredDirection, desiredPower,
   curl-план, высоту)`, которые кладутся в `TouchInfo`. Физическую скорость по-прежнему
   считают `GetShotVector`/`GetBestPossibleTouch` в момент касания анимации; curl становится
   **входом** в `GetShotVector` вместо случайного `zRot` (`humanoid_utils.cpp:502`). Зовут и
   `HumanController`, и `ElizaController` (set-piece ветка `elizacontroller.cpp:135-252` —
   кандидат на замену inline-логики). Магнус в мяче уже есть и всегда включён
   (`ball.cpp:484-501`); спин подаётся через `Ball::SetRotation` (`ball.cpp:119`).
   Планируемый curl меняет траекторию → gameplay → хеш `tools/determinism` поплывёт.
5. **Фазовая граница.** Презентация — поставщик состояния; `PlayerCommand`/`TouchInfo`
   собирает `HumanController` (в фазе Get), как и раньше. Дисциплина Get→Process→Put и
   условие конца стандарта не меняются.
6. **HUD.** Презентация отдаёт состояние (точка прицела, ratio заряда, роль); отрисовка
   ретикла/power-bar — отдельно, за гейтом роли.
7. **Активация и сеть.** На хосте роль/тип читаются из `RefereeBuffer`. На тонком клиенте
   (`Match::Process` early-return, `match.cpp:1213`) идентичность стандарта берётся из
   снапшота (v15, §1). Сеть-синк самих презентаций остаётся out of scope.

## 3. Управление бьющим: автопереключение, designated, Switch

Источники: [Автопереключение и designatedPossessionPlayer на стандартах](https://github.com/polite-cat-2001/GameplayFootball/issues/15),
[Смена бьющего на стандарте через меню (Share/Tab)](https://github.com/polite-cat-2001/GameplayFootball/issues/18).

**Бьющего ставит автопереключение, не презентация.** `Team::UpdateSwitch` остаётся
единственным местом, которое ставит управление на designated-игрока; презентация §2 только
читает «управляемый == `RefereeBuffer.taker`». Две правки:

1. Звать `UpdateSwitch` вне `IsInPlay()`. `Match::Process` вызывает
   `teams[i]->UpdateSwitch()` безусловно (`match.cpp:1262-1263`), но внутренний гейт
   `match->IsInPlay()` (`team.cpp:644`) блокирует работу в стандарте. Автопереключение на
   стандарте должно исполняться.
2. Снять вратарский запрет **на стандарте**: `team.cpp:646`
   (`if (designatedTeamPossessionPlayer != GetGoalie())`) и гейт ручного переключения
   (`team.cpp:493`) разрешают выбирать вратаря только на стандарте, когда он и есть
   designated/бьющий. В открытой игре запрет остаётся.

**Designated на стандарте = бьющий.** Отдельной сущности «тэйкер стандарта» не заводим:
`designatedPossessionPlayer` и `designatedTeamPossessionPlayer` отыгрывающей команды на
время стандарта указывают на `RefereeBuffer.taker`.

- **Хост:** при входе в стандарт форсим `designatedTeamPossessionPlayer` отыгрывающей
  команды — иначе блок `match.cpp:1284` («just stick with current team») может залипнуть на
  игроке обороняющейся команды; синхронно правим `designatedPossessionPlayer`.
- **Блок `match.cpp:1272-1288` пропускается при `IsInSetPiece()`**: его `timeRating < 0.85`
  иначе затирает выбор автопереключения. Порядок `UpdateSwitch` → `Process` →
  `UpdatePossessionStats` не трогаем.
- **Клиент:** `ApplyRemoteSnapshot`, увидев `e_SetPiece != None`, ставит
  `designatedPossessionPlayer` (и `designatedTeamPossessionPlayer` своей команды) в
  снапшотного бьющего (team+slot, v15), а не по близости (`match.cpp:1595`). Иначе
  `remoteCameraOverride` (`match.cpp:1606`) и локальный HUD берут не того.

**Switch на стандарте подавлен**: пока `IsInSetPiece()`, кнопка `Switch` не переключает
игрока (`team.cpp:475-499`) — она занята chip-комбо (§5) и воровала бы бьющего.

**Два локальных игрока**: бьющий достаётся первому в очереди `switchPriority`
(round-robin `SelectPlayer`, `team.cpp:397`).

**Смена бьющего через меню** (закрыто сразу в #18): меню игроков команды (включая вратаря)
меняет **фактического бьющего текущего стандарта**, только для открывшего его бьющего-человека,
управление остаётся за ним. Кнопка — существующая `e_ButtonFunction_Select` (геймпад Share,
клавиатура `Tab` вместо `F1`). Навигация стрелки/WASD, применить Enter, закрыть Escape; вне
стандарта — no-op. Локально у пира, намерение хосту по существующему input-каналу.

**Вратарь-тэйкер на пенальти.** `Keeper`-роль (§2) управляемым вратаря не делает: он
по-прежнему ИИ, намерение сайд-каналом (§9). Снимается только запрет **выбора вратаря как
designated на стандарте**.

## 4. Камеры стандартов

Источник: [Камеры стандартов](https://github.com/polite-cat-2001/GameplayFootball/issues/5).

**Область.** Set-piece-камера — только для пенальти, штрафного, углового и удара от ворот.
Аут и кикофф камеру не меняют (аут слишком короткий; кикофф делит момент со scorer-cam и
extended replay). Роли презентации `Kicker`/`Keeper` остаются для всех шести типов — сужен
только набор камерных поз.

**Шов применения.** Override-паттерн фол-камеры: презентация при владении камерой выключает
авто-камеру (`SetAutoUpdateIngameCamera(false)`) и каждый тик перезаписывает 6 живых полей.
Добавляется аппликатор `SetSetPieceCamera(eye, lookAt, fov, nearCap, farCap)`, раскладывающий
look-at в существующую композицию (yaw → `cameraNodeOrientation`, pitch → `cameraOrientation`,
позиция → `cameraNodePosition`). `FollowCamera` не трогаем.

**Активация и приоритет.** Камера включается в `prepareTime` (тэйкер уже известен,
`restartPos` зафиксирован) и живёт до релиза — уже на выстройке игроков, до свистка.
Film-referee-cam (foulType 2/3) владеет окном до `prepareTime` и в этой точке передаёт
управление. Scorer-cam сохраняет безусловный приоритет (при исключённом кикоффе пересечения
нет).

**Позы.** Оси GF: x — длина (линия ворот `±pitchHalfW`), y — ширина, z — вверх.

- Общий случай: `eye = spot − heading*BACK + (0,0,HEIGHT)`,
  `look = spot + heading*AHEAD + (0,0,LOOK_Y)`.
- Пенальти: `eye = spot − forward*BACK + (0,0,HEIGHT)`, `look = (goalLineX, 0, LOOK_Y)` —
  центр ворот.
- `spot` — точка мяча на момент активации (`buffer.restartPos`, обнулённый по z),
  замораживается.
- `forward`/`heading` — горизонтальный единичный вектор: пенальти — от спота в центр ворот;
  штрафной/угловой/от ворот — направление прицела (базовое — от спота в центр ворот,
  поворачивается прицелом).

**Взгляд.** Пенальти — фиксирован в центр ворот. Штрафной/угловой/от ворот — вращается с
прицелом и замораживается в момент коммита удара (отпускание кнопки, а не касание мяча).

**Камера вратаря на пенальти.** `Role.Keeper` получает ту же камеру за бьющим; отдельного
ракурса нет.

**Сглаживание и релиз.** Дополнительного блендинга нет: живые поля сглаживает существующий
`TemporalSmoother` (20 мс); вход — кат (как фол/scorer), выход —
`SetAutoUpdateIngameCamera(true)` (сброс `camPos`).

- Пенальти — всегда держим 1.5 с после отпускания кнопки и смотрим полёт, даже если мимо.
- Штрафной — если действие удар, держим 1.5 с; если пас/навес — камера уходит в момент
  отпускания кнопки.
- Угловой и от ворот — всегда уходят в момент отпускания кнопки.
- Во время просмотра камера неподвижна (заморожена на момент удара), за мячом не едет.
- Предсказание траектории «в створ» не нужно: тип действия (удар vs пас/навес) уже известен
  из ввода.

**Сеть.** Камера — корзина C: строится локально тем пиром, чей живой человек владеет ролью.
Не-владельцы продолжают получать host-камеру из снапшота. На тонком клиенте
(`Process` early-return) локальная камера строится в `ApplyRemoteSnapshot`.

**Детерминизм.** Камера — presentation-only, хеш не меняет.

## 5. Маппинг ввода

Источник: [Маппинг ввода: curl/chip и действия вратаря](https://github.com/polite-cat-2001/GameplayFootball/issues/4).

Поддержка FIFA/PES-пресетов удаляется — одна PES-like раскладка геймпада. Кнопки раздачи
вратаря ключуются от семантических `e_ButtonFunction`, поэтому PES/FIFA-специфика уходит сама.

### Итоговая таблица «действие → клавиатура → геймпад»

| действие | клавиатура | геймпад (PES-like) |
|---|---|---|
| curl (модификатор + Shot) | `C` + `D` | `R2` (Dribble) + Shot |
| chip (модификатор + Shot) | `Q` + `D` | `L1` (Switch) + Shot |
| switch player (защита) | `Q` | `L1` |
| attacking run (атака) | `Z` | `L2` (Special) |
| стоп-на-месте (атака) | `Z` | `L2` (Special) |
| super-cancel (без мяча) | `Z` | `L2` (Special) |
| knock-on | двойной тап `E` | двойной тап `R1` |
| sprint | `E` | `R1` |
| dribble | `C` | `R2` |
| вброс руками (тап = раскат низом / hold = бросок верхом) | `S` | `A` (ShortPass) |
| выбивание ногой в центр | `D` | `X` (Shot) |
| выбивание ногой по стику | `A` | `B` (HighPass) |
| «в ноги» → полевой | `W` | `Y` (LongPass) |

### Варианты удара (curl/chip)

- curl = `R2`(Dribble)+Shot / `C`+`D`; chip = `L1`(Switch)+Shot / `Q`+`D`.
- Модификатор сэмплируется в момент **нажатия** Shot и несётся в команду; действует и для
  обычного, и для одно-касания/queued удара.
- Если зажаты **оба** модификатора → обычный удар (`Normal`).
- Новый enum `e_ShotType { e_ShotType_Normal, e_ShotType_Curl, e_ShotType_Chip }` в
  `src/gamedefines.hpp` + поле в ударной команде рядом с `desiredDirection`/`desiredPower`.
- Новых `e_ButtonFunction` не заводим — переиспользуем существующие (`defaultKeyIDs` /
  настройки не трогаем).
- При заряде chip подавляем edge-переключение игрока; при заряде варианта удара подавляем
  knock-on/super-cancel.

### Раздача вратаря (4 действия)

- **Рука** (`ShortPass`): стик задаёт направление; тап (заряд < порога) = раскат низом
  ближнему, hold = бросок верхом дальнему; удержание = дистанция; цель выбирается среди
  партнёров в направлении стика.
- **Нога-в-центр** (`Shot`): мгновенно, фиксированная сила, в центр.
- **Нога-по-стику** (`HighPass`): стик задаёт направление, заряд = дистанция.
- **«в ноги»** (`LongPass`): мяч к своим ногам, вратарь становится полевым (§8).
- Константы: `keeperHandThrowCharge_ms = 200` (порог тап/hold) + дальности раската/броска.
- Контекст активен, когда управляемый игрок — вратарь, удерживающий мяч. Включение
  управления вратарём — §8.

### Изменения существующих биндов (`src/onthepitch/player/controller/humancontroller.cpp`)

- attacking-run (`:462`) и стоп-на-месте (`:507`) переезжают с `Switch` на `Special` (L2/Z).
- super-cancel (`:319-325`) переезжает с `Dribble+Sprint` на `Special` (L2/Z), условие
  `!hasBestPossession`.
- knock-on (`:257`) переезжает с `Dribble+Sprint` на **двойной тап Sprint** (нужна
  инфраструктура двойного тапа в `HumanController` + константа окна).
- Комбо `Dribble+Sprint` исчезает полностью; `Dribble` остаётся ведением и модификатором
  curl.
- Владелец `L2`/`Z` — «ручной режим»: с мячом → рывок партнёра + стоп, без мяча → снятие
  автоподсказки.

### Удаление раскладок PES/FIFA

- `src/gamedefines.hpp:39-44` (`e_ControllerLayout`, `defaultControllerLayout`),

## 6. Прицеливание подач со стандартов

Источник: [Прицеливание штрафной/угловой/от ворот](https://github.com/polite-cat-2001/GameplayFootball/issues/6).

**Наведение.** Стик-X проворачивает world-вектор направления подачи вокруг мяча (поворот 2D),
без сброса при отпускании — прицел остаётся там, куда наведён. Предел угла: **штрафной —
полный оборот**; **угловой** и **от ворот** — сектор вперёд (`CORNER_AIM_ARC` 1.4 и
`GK_AIM_ARC` 1.2 рад). Скорость поворота — 1.6 рад/с, мёртвая зона стика 0.15. Стартовое
направление: штрафной — центр ворот; угловой — 11-метровая отметка; от ворот — вперёд по полю.

**Виды подач** (кнопка в момент нажатия задаёт вид, длительность удержания — силу/дальность):

- штрафной: `ShortPass` (низом на партнёра), `LongPass` (пас на ход низом), `HighPass`
  (навес), `Shot` (удар);
- угловой: `ShortPass` (низом), `HighPass` (навес в штрафную);
- от ворот: `ShortPass` (низом), `HighPass` (навес вперёд);
- аут и кикофф — вне этой модели (аут уже работает, кикофф — принудительный короткий пас).
- **Черпачок на стандартах не используется** — остаётся модификатором только в открытой
  игре (§5).

**Высота.** `Shot` (только штрафной): заряд задаёт и силу, и угол вылета — две оси из одного
заряда (скорость 36→46 м/с, угол 4°→22°). Все прочие подачи: высоту задаёт стик-Y
(вверх-вниз), а удержание — силу/дальность. Удару стик-Y не назначается.

**Закрутка.** Копится боковым стиком **с момента нажатия кнопки подачи до касания мяча**
(включая разбег). Действует на **любую подачу** — пас, навес, удар. Это не комбинация кнопок.

**Ассист.** Только у удара штрафного: направление на 18% подмешивается к центру ворот
(`goal_magnet`). Случайный scatter не переносим — в GF уже есть свой разброс в
`GetShotVector`. У углового / от ворот магнетизм не применяется.

**Выражение в коде.** Модель — чистый модуль `SetPieceLogic` (§2), возвращает
`(desiredDirection, desiredPower, высота, curl)`. В ударный путь: `TouchInfo` получает поля
высоты вылета и curl; `GetShotVector` использует их вместо фиксированной высоты `0.05` и
случайного `zRot` (`humanoid_utils.cpp:457,515`). Физика закрутки/черпачка — §7.

**Границы.** Модель общая, зовёт и человек, и ИИ; поведение ИИ-тайкера — §12. Пенальти — §7
(2D-ретикл, эта модель к нему не применяется) либо вратарь-человек.

## 7. Модель удара: curl, chip и прицел пенальти

Источники: [Curl/chip через SetRotation и Magnus](https://github.com/polite-cat-2001/GameplayFootball/issues/8),
[Прицел пенальти](https://github.com/polite-cat-2001/GameplayFootball/issues/9).

### Обычный удар и curl (общий путь `Humanoid::GetShotVector`)

- **Баллистический пуск в точку на линии ворот.** Точка прицела — пересечение направления
  удара с плоскостью своих атакующих ворот (`x = side * -pitchHalfW`), латераль клампится.
- **Высота прицела растёт с зарядом:** `AimYMin 0.8 м → goalHeight + OverLift = 3.5 м`.
- **Вертикальная скорость — из баллистики** (`t = dist / v`, `vz = Δz / t + ½g·t`), с
  потолком `MaxLift = 6 м/с`. Горизонталь = `power` (стат-зависимая, ~31–45 м/с).
- **Короткий тап — низом.** Заряд < `GroundChargeMax = 0.35` (шкала `desiredPower`) →
  настильный удар, вертикаль обнуляется, скорость не ниже `GroundPower = 60 м/с`.
- **Время заряда удара 0.5 с** (`KICK_CHARGE_MAX_TIME`); у пасов остаётся 1 с. Автовыстрел на
  полном заряде.

**Типы удара:**

- **Curl** — удерживаемый модификатор: доворот прицела наружу `AimOut = 0.1 рад` + боковое
  вращение `ZRot = 90`. Работает и низом, и верхом (низовой обнуляет только вертикаль,
  вращение остаётся).
- **Chip** — отдельная высокая дуга (`Chip_Loft = 8 м/с`, `Chip_HorizFactor = 0.55`); низом
  не режется.
- **Double-tap низом** — отвергнут: в GF удар летит на отпускании, окно «до касания» ~80 мс,
  флаг не успевал ставиться. Принята модель эталона: низом = короткий тап.

**Анимации:** новых не нужно — и curl, и chip используют существующий клип `shot`;
различие только в векторе касания мяча и его вращении (`SetRotation`).

**Дефолты:** `shot direction assist = 0.74`, `curl spin = 90`, `curl aim offset = 0.1`.
`curl spin` и `curl aim offset` выносятся в настройки геймплея ползунками (с показом числа).

### Прицел пенальти (отдельно от §6)

- 2D-прицел `Vector3 penaltyAim` (латераль, высота) на плоскости своих атакующих ворот.
  Стик двигает точку со скоростью 6 м/с, кламп `±(goalHalfWidth+0.6)` и
  `0..(goalHeight+0.6)`; без ввода — плавный возврат к центру (12/с). Горизонталь
  инвертирована, чтобы совпасть с экраном.
- **Фиксация в момент нажатия** удара: маркер замирает; удар летит в эту точку + выборка из
  диска разброса (0.15→1.6 м по заряду), скорость пуска 24→44 м/с. После разыгрыша стандарта
  маркер сбрасывается.
- **Авто-аим отключён** (`AI_GetShotDirection` для пенальти не применяется). В `GetShotVector`
  добавлена ветка `TouchInfo.useAimTarget` (латераль/высота/скорость из `TouchInfo`, без
  worst-case и боковой кривой, потолок вертикали снят).
- Жёлтый дебаг-маркер (`SetYellowDebugPilon`).
- Дебаг-активация: клавиша `P` (полный набор — §11).

## 8. Игра за вратаря

Источник: [Вратарь: руки, бег, распределение](https://github.com/polite-cat-2001/GameplayFootball/issues/7).

Строится **отдельным GF-native слоем** поверх существующего владения, без параллельной
иерархии контроллеров и без новых типов команд.

1. **Слой и состояние.** Новый каталог `src/onthepitch/keeper/`: стейт-машина
   `e_KeeperState { None, Hands, Outfield, Returning }` + чистый расчёт
   (`keeperlogic.{hpp,cpp}`): кламп штрафной, выбор цели раздачи, точка приземления.
   Состояние — host-sim gameplay, владеется `Match` рядом с `ballRetainer`.
   `Match::SetBallRetainer` (`match.hpp:404`) остаётся **единственной правдой** о владении:
   ловля по-прежнему ставит его (`humanoid.cpp:616`), владение/designated-игрок текут из него
   (`player.cpp:292-303`, `match.cpp:1287`). Приклейка мяча к кости (`humanoid.cpp:648-665`)
   не трогается.
2. **Команды — без новых `e_FunctionType_*`.** Новый клип не нужен, механика вброса уже есть
   (это аут). `Humanoid::SelectRetainAnim` (`humanoid.cpp:1087`) ставит retainer и выбирает
   throw-клип по retain/special-состоянию; ловля вратаря оседает на том же `right_elbow`.
   Значит:
   - **Вброс руками** — `ShortPass`/`HighPass` (+ throw-клип); тап = раскат низом, удержание =
     бросок верхом.
   - **Нога в центр / по стику** — существующие типы (`Shot` / `HighPass`).
   - **«В ноги»** — перехват кнопки (`LongPass`) стейт-машиной → `Hands → Outfield`, ударная
     команда не шлётся.
   - **Ловля** — существующий `e_FunctionType_Deflect` + `onlyDeflectAnimsThatPickupBall`
     (`playercontroller.cpp:257` → `humanoid.cpp:616`).
3. **Включение управления.** Вратарь перестаёт быть вырезанным точечно:
   - **Ловля**: когда вратарь становится retainer во время игры — форсируем его выбор для
     локальной человеческой команды (исключение к вратарскому пропуску в `team.cpp:646`).
   - **Бэкпас**: вратарь выбирается заранее, когда он — designated possession игрок и
     получает пас от партнёра; снимаем исключение `team.cpp:646` только под это условие.
     Вне этих двух случаев в открытой игре вратарь остаётся под ИИ.
   - Пока `Hands` — переключение игрока заперто. Двое локальных игроков: вратаря берёт тот,
     чья очередь `switchPriority` владеет designated-игроком (`team.cpp:644-650`).
   - У команды без человека поведение прежнее: вратарь-ИИ (`Elizacontroller` GK-ветка,
     `elizacontroller.cpp:287-306`, `GoalieDefaultStrategy`).
4. **`Hands` (мяч в руках).** Жёсткий кламп позиции штрафной площадкой (переиспользуем
   существующее приближение из `_KeeperDeflectCommand`, `playercontroller.cpp:249-251`:
   глубина 16.4 м, полуширина 20.05 м — выносим в именованные константы). Бег с мячом в руках
   обычной локомоцией; мяч остаётся приклеен к кости.
5. **`Outfield` («в ноги») и `Returning`.** По кнопке «в ноги» мяч уходит к ногам, вратарь —
   полевой: клэмп снят, обычные ведение/пас/удар. **Обратный пас**: в руки нельзя
   (`playercontroller.cpp:242-246`), мяч принимается ногами как полевым. Потеря мяча →
   `Returning`: вратарь бегом возвращается на позицию (не телепорт), управление **сразу**
   уходит полевому игроку через обычное автопереключение.
6. **Правило 6 секунд.** Таймер стартует на ловле (`Hands`). По истечении — принудительный
   вынос **в центр** (как `CLEAR_CENTER` в open_football), затем управление отдаётся
   **ближайшему партнёру к точке приземления**. Событие и физика — на хосте.
7. **Хэндофф после раздачи.** После ручного вброса/выноса управление **сразу** переходит на
   партнёра-адресата. После автовыноса по 6 с — на ближайшего к приземлению.
8. **Прицел.** Стик задаёт направление; игра сама выбирает партнёра в этом направлении
   (скоринг «направление × полоса дальности», заряд = дальность). 2D-ретикла нет; камера и
   HUD обычные, полоску силы и отсчёт не рисуем. Слой презентации §2 для игры за вратаря не
   расширяется.
9. **Сеть.** Выбор игрока — локальный на каждом пире, `ownerId` синкается для раскраски,
   снапшот не меняем. Клиент видит мяч у вратаря из позы (приклеенный мяч + клип ловли) и
   локально форсит выбор/HUD-логику. Таймер 6 с и физика раздачи — host-sim.

**Границы.** §9 (нырок при пенальти) — отдельно; сюда входит только переход ловля→`Hands`
(после сейва в т.ч.). Общее автопереключение и `designatedPossessionPlayer` — §3; здесь только
вратарское исключение и бэкпас-выбор.

## 9. Оборона пенальти: вратарь-человек и ИИ

Источник: [Оборона пенальти: вратарь — человек и ИИ](https://github.com/polite-cat-2001/GameplayFootball/issues/13).

**Управление (человек и ИИ).** Вратарь остаётся под ИИ (ветка Eliza-контроллера);
`controlled_player` не меняем. Намерение человека — отдельное значение, которое потребляет
**один** путь вратаря; источник — стик человека или случайная зона ИИ. ИИ-тайкер через
презентацию не идёт.

- Направление стика берётся из уже передаваемого потока: клиент снимает сырое направление
  устройства каждый тик (`netmatchsession.cpp:316-323`) и шлёт на хост.
- Один стик: до удара ось X ведёт вратаря вдоль линии; в момент касания текущий стик X+Y
  выбирает зону; мёртвая зона → CENTER.
- Смещение по линии — до штанги: кламп `±(GOAL_WIDTH/2 − 0.5)`, скорость 3.0 м/с.
- Зона защёлкивается и нырок стартует **в момент касания мяча бьющим** — то же событие, что
  гасит стандарт (`referee.cpp:238-242`).

**Зоны и ИИ.** 5 зон: `LOW_L`, `HIGH_L`, `LOW_R`, `HIGH_R`, `CENTER`. `CENTER` — не боковой
прыжок, а центральная реакция по высоте (низ — ловля, верх — отбой). ИИ-зона — **симметричный**
взвешенный случай: низ **25%** на сторону, верх **12%** на сторону, центр **26%**. Берётся из
существующего детерминированного `random()` (`src/base/math/bluntmath.cpp`; харнесс сеет
`randomize(42)`, `tools/determinism/main.cpp:98`). L/R для **выбора клипа** — от локальной
ориентации вратаря (`basis.x`); вероятности симметричны, поэтому ориентация на веса не влияет.

**Механика нырка.**

- Нырок выполняется **всегда**; пенальти-режим вратаря перекрывает чтение реального мяча до
  касания и приоритетен над обычным goalie-AI на время нырка, затем вратарь возвращается к
  штатному поведению.
- **Цель нырка**: если зона реального полёта мяча совпала с выбранной (угадали) — цель
  **заменяется реальным перехватом летящего мяча**; если не совпала — прыжок в представительную
  точку выбранной зоны (в пустоту). Случайного разброса внутри зоны нет.
- **Реализация**: в путь `deflect` подставляется синтетическое предсказание мяча — тогда
  штатное корневое движение клипа + `actionSmuggle` уводят тело; новой физики прыжка нет.
- Клип выбирается по высоте/стороне зоны: низкие зоны ловятся (`ground`/`kneeheight holdball`),
  верхние отбиваются; сторона — из `basis.x`.
- **Искусственных «неберущихся» порогов нет**: ловля/отбой/гол решает естественная геометрия и
  существующая сложность `(1 − veloDifficulty) × (1 − reactionDifficulty) < 0.3f`
  (`humanoid.cpp:599-612`). Промах зоной = нет касания = гол.

**Сеть и детерминизм.** Протокол и снапшот не меняются (v15 из §1 относится к стандарту, не к
нырку). Это gameplay-изменение → эталоны `tools/determinism` перегенерируются.

## 10. Стенка при штрафном у своих ворот

Источник: [Стенка при штрафном у своих ворот](https://github.com/polite-cat-2001/GameplayFootball/issues/14).

Направление: стенка остаётся под ИИ, человеческого управления не вводим.

**Находки.**

- **Прыжка игрока в GF нет.** Симуляция строго 2D (z == 0, иначе фатальная ошибка,
  `humanoid.cpp:338`); высоту тела задаёт только z-канал кости `player` в анимации
  (`animation.cpp:641-716`). Механизма «поднять тело кодом» не существует.
- **Столкновение мяч↔игрок трёхмерное** — сфера-vs-AABB по позным костям
  (`match.cpp:2479-2487`); скриптовый Interfere/Deflect гейтится высотой
  (`ballDistanceZ < 0.22f`, `humanoid.cpp:2149`). Реально поднятое анимацией тело меняет
  перехват; «подъём только в рендере» не работает.

**Решения.**

1. **Модель прыжка — анимация, а не код.** Переиспользуем существующий клип прыжка (подъём
   ~0.3 м); число «высота прыжка» не заводим. Новый клип — только если 0.3 м окажется мало,
   отдельным усилием.
2. **Число игроков** — дальше 40 м стенки нет, ближе 25 м — 4 игрока, между — линейно, минимум 2.
3. **Линия и шаг** — стенка на линии мяч→ближняя штанга (side-aware, `goalHalfWidth`), ровным
   рядом с шагом 0.62 м; прежний веер `0.07` удаляем. Мяч ближе 9.15 м к воротам — ряд на
   линии ворот.
4. **Кто в стенке** — N ближайших полевых игроков; вратаря исключаем, игрока под управлением
   человека не трогаем.
5. **Триггер прыжка** — высото-независимый, одна команда на всю стенку, порог = половина
   `freeKickWallJumpTime` (0.25 с) до подлёта, только если мяч летит в стенку; повторно не
   прыгать. Команду выдаёт `TeamAIController`; анимация проигрывается путём форс-анимации вне
   мяча (`e_FunctionType_Special`).

## 11. Разбег бьющего и дебаг-активация

Источники: [Разбег бьющего перед исполнением стандартов](https://github.com/polite-cat-2001/GameplayFootball/issues/17),
[Дебаг-активация стандартов для тестирования](https://github.com/polite-cat-2001/GameplayFootball/issues/12).

### Разбег бьющего

**Аудит клипов — новые не нужны.** `.anim` — текстовый формат; смещение мяча на кадре касания
(`extension,football,<frame>`):

| клип | кадр касания | смещение мяча | ход корня `player` |
|---|---|---|---|
| `shot\idle\020.anim` | 25 | ≈ 0.99 м | ≈ 0.85 м |
| `shot\walk\090_2step.anim` | 28 | ≈ 2.16 м | ≈ 2.45 м |
| `shot\sprint\090_2step.anim` | 29 | ≈ 2.27 м | ≈ 3.03 м |

Дистанция разбега задаётся выбранным клипом удара — его смещением мяча на кадре касания.
Отдельный root-motion-клип не нужен.

- **Дистанция.** Пенальти: `_default_SetPiece_RunupDist = 2.2 м` за мячом + латеральный сдвиг
  `_default_SetPiece_RunupFootLateral = 0.4 м` под опорную ногу.
- **Разбег ↔ касание ↔ заряд.** Разбег ведёт обычная система движения (спринт-команда к мячу),
  а удар **придержан** до добегания (`_default_SetPiece_KickReach = 1.1 м`), затем срабатывает
  штатный удар и клип доводит ногу до мяча. У человека заряд совмещён с разбегом (держишь
  кнопку — бежит; отпустил/добёг — бьёт).
- **Шов и модель.** Разбег живёт в контроллере, не в презентации; модуль
  `src/onthepitch/setpiece/` для него не нужен — презентация лишь читает позицию бьющего.
- **Коридор за бьющим.** В `Referee::PrepareSetPiece` — расчистка коридора пенальти
  (полуширина 1.5 м, до 6 м за мячом, запас 0.4 м) — обобщение лана штрафного из #12.
- **Область.** Разбег нужен **только пенальти и штрафному**. Угловой и удар от ворот — **без
  разбега**, бьющий вплотную к мячу. В реализацию уезжает обобщение разбега на штрафной и на
  ИИ-бьющего (механизм тот же).

### Дебаг-активация стандартов

Клавиши работают только из чистого игрового состояния (не во время стандарта и не во время
празднования гола):

- `P` / `Alt+P` — пенальти в атакуемые / в свои;
- `F` / `Alt+F` — штрафной в атакуемые / в свои;
- `Y` / `Alt+Y` — угловой в атакуемые / в свои;
- `F2` — убрать полевых соперников за поле (вратарь остаётся), обратимо.

`Alt`-варианты отдают стандарт ИИ-сопернику. `Referee::DebugForceSetPiece(e_SetPiece, teamID,
restartPos)` только выставляет буфер судьи и запускает штатный `PrepareSetPiece` +
`StartPlay/StartSetPiece`; бьющего выбирает и передаёт человеку обычный флоу
(`TeamAIController::PrepareSetPiece` + `Team::UpdateSwitch`). `Match::Process` опрашивает
`SDL_K_P/F/Y`; `Alt` — через `SDL_GetModState()`.

**Побочно (gameplay):** на штрафном партнёр бьющей команды стоял на линии удара (пре-существующее
поведение GF). Портирован подход open_football `_clear_ball_to_wall_cone`: лана = коридор
разбега за мячом + конус через два крайних игрока стенки; выталкивание **перпендикулярно** лучу
удара + дополнительно половина дистанции мяч→стенка. Константы `_default_FreeKick_Lane*`.
Хеш `tools/determinism` поплывёт.

## 12. ИИ-тайкер стандартов

Источник: [ИИ-тайкер: использование общего расчёта удара и стандартов](https://github.com/polite-cat-2001/GameplayFootball/issues/16).

**Область**: ИИ-тайкер на **пенальти** и **штрафном**. Аут, кикофф, угловой, от ворот —
поведение без изменений. **Chip** на стандартах не применяется.

**Архитектура**: чистые функции-планировщики в `src/onthepitch/setpiece/`; `ElizaController`
только собирает `PlayerCommand`; ИИ идёт напрямую, минуя презентацию.

**Штрафной (ИИ-тайкер):**

- Прямой удар, если точка в радиусе (~≤30 м до ворот) и угол на створ в секторе ~±50°; иначе —
  подача.
- Тип удара: **50% curl** (обвод стенки) / **50% прямой силовой**.
- Прицел: **90%** угол, закрытый стенкой (обходят закруткой); **10%** вратарский угол.
  Высота: **95%** верхний угол, **5%** низом под стенкой.
- Curl фиксирован в сторону выбранного угла, величина — константа; сила — по дистанции.
- Если не удар: навес в штрафную по умолчанию; низом — когда рядом открытый партнёр. Адресат
  — партнёр с лучшей оценкой «открытость + выдвинутость вперёд» (чистая функция), **вместо**
  нынешних случайных точек и `AI_GetClosestPlayer`.

**Пенальти (ИИ-тайкер)**: прицел — угол (случайная сторона) или центр; сила случайная, чаще
высокая; curl/chip нет. Оборона пенальти — §9.

Используется существующий `random()`; gameplay-правки → перегенерация эталонов.

## 13. Сетка (NetSim)

Источник: [Колыхание сетки: NetSim и процедурный меш](https://github.com/polite-cat-2001/GameplayFootball/issues/10).

1. **Модель.** `NetSim` из `open_football` (`scripts/match/net_sim.gd`) переносится **1:1** в
   C++ как чистая математика: процедурная коробка из 4 независимых панелей (задняя / верх /
   левый бок / правый бок; низ открыт), внешнее кольцо каждой панели пиннится к каркасу,
   `slack` укорачивает `rest_len`, шаг — Verlet + soft-PBD. Модуль **не читает константы**:
   тюнинг приходит параметрами (headless-тестируем).
2. **Габариты — GF-шные**: ширина 7.4 (`goalHalfWidth=3.7`), высота 2.5 (`goalHeight`),
   глубина 2.55 (`goalDepth`). Плотность — 24×12×5 → **631 узел, 1155 рёбер, 198 пинов**.
3. **Симуляция включена постоянно** (не только `start_sim()` на гол): колыхание при навесе и
   при касании сетки снаружи.
4. **Связь односторонняя (presentation-only).** Мяч → сетка: `NetSim` берёт `ball_pos`/
   `ball_speed`. Обратного импульса нет, мяч гасится стопперами как сейчас. Хеш
   `tools/determinism` не меняется, net-sync сетки не нужен.
5. **`NET_BOUNCE = 0.1`** (было 0.15).

**Находки для реализации.**

- `ball.cpp:333-408`: флаг `ballTouchesNet` выставляется только внутри веток `ballIsInGoal` —
  под постоянную симуляцию триггер расширить на любое касание плоскостей сетки (включая
  снаружи), посылая `pos`/`vel` мяча в `NetSim`.
- Процедурный grid-меш на **каждый** гол вместо общего импортированного `.ase` с фильтром по x
  (`match.cpp:2634-2651`); рендер — динамический VBO + `OnUpdateGeometryData`/
  `UploadGoalNetting` (`match.cpp:2705-2709`); частота апдейта = тик.
- Открытый хвост (не блокирует): замерить стоимость аплоада VBO на 631 узле / 1155 рёбрах в
  реальном рендере.

## 15. Фазы реализации

Порядок предложен по зависимостям; каждая фаза — самостоятельный набор коммитов, собираемый и
проверяемый вручную. Пометка в скобках — тикеты-источники.

1. **Фундамент ввода и протокола.** `e_ShotType` + маппинг curl/chip, снятие PES/FIFA-раскладок,
   switch на `Special`/двойной тап, снапшот `v14→v15` (`e_SetPiece` + тэйкер), клиентская
   активация презентации из снапшота. (§1, §5)
2. **Общий расчёт удара.** `src/onthepitch/setpiece/setpiecelogic` + баллистика `GetShotVector`,
   curl/chip, низом-тапом. (§2, §7)
3. **Прицел пенальти.** 2D-ретикл, `useAimTarget`, дебаг-маркер. (§7)
4. **Шов презентации + камеры + прицел подач.** Объект презентации, роли, `SetSetPieceCamera`,
   наведение/виды подач/высоты/закрутка. (§2, §4, §6)
5. **Управление бьющим.** `UpdateSwitch` вне `IsInPlay`, designated = тэйкер, подавление Switch,
   клиент из снапшота, меню смены бьющего. (§3)
6. **Вратарь.** Слой `keeper/` (Hands/Outfield/Returning), включение управления, раздача, 6 с,
   хэндофф; нырок и зоны пенальти. (§8, §9)
7. **Стандартная оборона.** Стенка штрафного + лана, разбег бьющего, ИИ-тайкер. (§10, §11, §12)
8. **Сетка.** Порт `NetSim`, процедурный меш, расширенный триггер `ballTouchesNet`. (§13)
9. **Хвост.** Дебаг-активация стандартов, перегенерация эталонов `tools/determinism` на всех
   платформах, обновление вики (`[[матч]]`, `[[константы]]`). (§11, §16)

## 16. Детерминизм и вики

**Эталоны `tools/determinism`.** Перегенерацию требуют gameplay-изменения: curl/chip (§7),
состояние вратаря (§8), нырок (§9), стенка и лана (§10, §11), разбег (§11), ИИ-тайкер (§12),
автопереключение/designated (§3), протокол v15 (§1). Камеры, прицел, ретикл и сетка — нет.
Эталоны платформозависимы и лежат в `docs/wiki/открытые-вопросы.md` (Windows x86/x64, Linux,
macOS arm64).

**Вики.** После реализации: механика — в `[[матч]]`, протокол v15 — в `[[сеть]]`, все константы —
в `[[константы]]`. До реализации страницы не трогать (описывают текущее состояние, не будущее).

## 17. Вне области этой карты

- Серия пенальти / shootout.
- Реплеи новых фич.
- Сетевой net-sync презентаций (камеры, прицел).
- ИИ-исполнение стандартов с тайкером-человеком.
- ИИ-поведение углового (выбор адресата, типы подачи, живая защита) — отдельные усилия.
- Двусторонняя физическая связь мяч↔сетка (сетка presentation-only; мяч гасится стопперами).
